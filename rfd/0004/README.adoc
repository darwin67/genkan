= RFD 4 Dynamic HEIC desktop wallpaper

== Goal

Extend Genkan's wallpaper presentation into the logged-in Wayland desktop and
support macOS-style dynamic HEIC wallpapers whose still images change with the
local time of day. Solar-position schedules are an optional enhancement. A user
who opts into solar behavior does not need to discover, configure, or supply
geographic coordinates to Genkan.

This work adds a desktop wallpaper runtime; it does not keep the greetd process
alive after login or make the greeter own any part of the selected desktop
session. The HEIC schedule and decode implementation is reusable by the login
and lock presentations, but desktop ownership remains a separate process and
Wayland role.

Implementation progress is tracked in
link:IMPLEMENTATION.org[the implementation checklist].

== Context

RFD 2 added continuous HEVC MOV wallpaper playback to the login and lock
presentations. The current wallpaper state decodes a bounded latest RGBA frame,
hands it to iced or the session-lock renderer, scales it to cover each output,
and retains the displayed frame after a presentation failure. Those frame and
failure boundaries remain useful, but a dynamic HEIC is not a video and should
not be passed through the MOV playback pipeline.

A macOS dynamic HEIC is a HEIF container with multiple top-level still images.
XMP metadata associated with its primary image carries an Apple-namespaced,
Base64-encoded binary property list. Relevant schedule properties are:

* `apple_desktop:h24`, a sequence of image indices and normalized local times;
* `apple_desktop:solar`, a sequence of image indices and authored solar
  altitude and azimuth values; and
* `apple_desktop:apr`, a light and dark appearance pair.

The compact property-list keys commonly used by compatible files are `ti` for
the time sequence, `si` for the solar sequence, `ap` for an embedded appearance
pair, `i` for an image index, `t` for a fraction of the local civil day, `a` for
solar altitude, and `z` for solar azimuth. Indices address positions in the
ordered top-level image collection; they are not HEIF item identifiers.

The format describes still variants and schedule points. It does not require a
particular Genkan animation between points. Smooth transition policy therefore
belongs to Genkan and must be deterministic independently of undocumented
macOS implementation details.

The existing `genkan login` process cannot become the desktop wallpaper
service. greetd starts the selected session only after the greeter exits, and
the desktop has a different Wayland connection, user identity, output
lifecycle, and failure boundary. Similarly, `genkan lock` temporarily owns
security-sensitive session-lock surfaces and must not remain the desktop
background owner after unlock.

Wayland has no universal set-wallpaper protocol. A client can provide a
wallpaper on compositors supporting the wlr layer-shell protocol; GNOME, KDE,
and other desktop shells may instead require shell-specific settings APIs. The
first implementation follows Genkan's existing niri and wlroots-oriented
deployment rather than presenting a compositor-independent claim.

== Decision

Genkan will add an explicit long-running desktop command:

[source,sh]
----
genkan wallpaper --file /absolute/path/to/wallpaper.heic
----

The command runs as the logged-in user, connects to that user's compositor,
creates a non-interactive background-layer surface for every output, and keeps
the selected wallpaper synchronized with local time. It does not authenticate,
contact greetd or PAM, select a session, request power operations, or acquire a
session lock.

The initial desktop backend requires wlr layer-shell and is supported on the
compositors for which that protocol behavior is verified. Unsupported
compositors fail with a bounded diagnostic rather than opening an ordinary
window above desktop content. Shell-specific GNOME and KDE integrations are
deferred.

Time scheduling through `h24` is the required dynamic behavior. Solar
scheduling is optional and uses GeoClue when the user enables the solar feature.
Genkan exposes the wallpaper feature choice, not GeoClue's provider URLs,
application authorization fields, requested source, or raw coordinates. NixOS
integration translates the high-level choice into the required GeoClue service
and application authorization.

Dynamic HEIC support will also fit behind the existing shared wallpaper state
so login and lock can adopt the same selected frames without duplicating
parsing or schedule rules. That reuse does not merge the desktop, greeter, and
locker top-level state machines.

[source,text]
----
                 shared dynamic-wallpaper engine
          HEIF reader, metadata, schedule, RGBA frames
                              |
              +---------------+---------------+
              |               |               |
              v               v               v
       genkan wallpaper  genkan login    genkan lock
       layer-shell       iced window     session-lock surfaces
       logged-in user    greeter user    logged-in user
----

== HEIC reader and validation

Genkan will use `libheif` through maintained Rust bindings to enumerate
top-level image items, inspect metadata, and decode selected items to RGBA. It
will not invoke ImageMagick, `heif-convert`, a shell, or an external wallpaper
process. The Rust `plist` crate will decode the binary property list after
bounded Base64 decoding, and a namespace-aware XML reader will inspect XMP.

The reader inspects all XMP MIME metadata blocks associated with the primary
image and ignores unrelated or unknown metadata. It validates the selected
Apple property before publishing a schedule:

* every referenced image position exists in the top-level image collection;
* image count, dimensions, decoded byte size, metadata size, and nested value
  count remain below explicit limits;
* times and solar values are finite and within their defined domains;
* decoded dimensions and pixel lengths agree without integer overflow; and
* duplicate schedule points, missing optional keys, and unknown future keys
  have deterministic behavior and cannot cause a panic.

The source path must be an existing absolute regular file. It is bound and
opened by descriptor so later pathname replacement cannot substitute a FIFO,
device, remote URI, or different file. Runtime parsing uses libheif's security
limits. A malformed or unsupported HEIC is a presentation failure, never an
authentication or unlock decision.

The implementation will not eagerly decode every image. At 3840 by 2160, one
RGBA8 frame occupies about 31.6 MiB; retaining sixteen decoded variants would
consume about 506 MiB before renderer and decoder working memory. Genkan keeps
only the displayed frame, the next required frame while a transition is active,
one bounded pending update, and decoder-owned working memory. An unused next
frame may be discarded when the schedule or output state changes.

== Time schedule

An `h24` entry's `t` value is interpreted as a fraction of the current local
civil day. Genkan obtains local date, clock, time zone, and daylight-saving
offset from the operating system. No geographic position is needed.

Entries are ordered by normalized time and treated as a circular sequence. The
last entry before the current local time is the current image; the next entry is
the transition target. Selection wraps across local midnight. A clock jump,
time-zone change, daylight-saving transition, suspend, or resume causes a fresh
selection from current civil time rather than replaying elapsed transitions.

The scheduler wakes at the next relevant boundary and also performs a bounded
periodic resynchronization so an external clock change cannot leave a stale
frame indefinitely. It does not redraw once per second while the same static
frame remains selected.

The default transition is a short dissolve between adjacent selected images.
It runs only around a schedule boundary and publishes through the same bounded
latest-frame handoff used by the existing wallpaper state. Reduced-motion mode
changes immediately at the boundary. Continuous interpolation over an entire
schedule interval is deferred until visual and resource evidence demonstrates
that it is preferable to a bounded transition.

== Optional solar schedule

Solar behavior is opt-in. Enabling it permits Genkan to request approximate
location from GeoClue and causes NixOS integration to enable and authorize the
corresponding GeoClue application identity. Genkan does not expose a location
provider selector, GeoClue configuration passthrough, latitude or longitude
fields, or geolocation-service URL.

City-level accuracy is sufficient for sunrise, sunset, and the visual solar
path. Genkan requests no greater accuracy, does not write the returned location
to disk, and never includes coordinates, nearby network identifiers, or raw
GeoClue errors in ordinary diagnostics. The documentation states that GeoClue
may use a network geolocation provider and that enabling solar behavior can
therefore result in location-related network requests according to host policy.

The wallpaper appears before location resolution completes. Location lookup
must not delay login, lock readiness, desktop startup, or wallpaper surface
configuration. After a successful lookup, Genkan computes the current solar
position from the current date and returned coordinates and selects the
adjacent authored `si` points on a circular daily solar path. The public
algorithm is compatibility behavior; Genkan does not claim bit-for-bit
equivalence with Apple's private implementation.

GeoClue denial, timeout, an unavailable service, unusable accuracy, polar-day
or polar-night edge cases, and a disconnected network all produce a visual
fallback rather than a daemon failure. If the file also contains a valid `h24`
schedule, Genkan uses it. Otherwise it displays the declared appearance or
primary static frame. It does not invent coordinates from the time-zone name or
silently map solar azimuth directly to clock time.

Desktop and pre-login consumers use separate GeoClue application identities.
The desktop command is an ordinary logged-in application. A future login-screen
integration is a system component restricted to the configured greeter UID
because no user-session authorization agent exists before login. Enabling
desktop solar behavior does not implicitly grant the greeter location access;
pre-login solar use requires a separate high-level Genkan opt-in.

== Appearance metadata

Standalone `apr` metadata and an appearance pair embedded in a time or solar
property are parsed and validated. The first implementation uses them as static
fallback choices and supports an explicit light or dark wallpaper preference.
Automatic synchronization with GNOME, KDE, or another desktop shell's theme is
not required for time-of-day support and is deferred until a portable signal is
identified.

== Desktop rendering and output lifecycle

The desktop command creates one background-layer surface per advertised output.
Each surface requests no keyboard focus, pointer interaction, exclusive desktop
area, or panel avoidance. It anchors to the complete output and redraws after
configure, scale, transform, and logical-size changes. Added outputs receive a
surface using the current selected frame; removed outputs release their local
surface and buffers without stopping the scheduler for remaining outputs.

Each output applies aspect-preserving cover semantics independently: scale
until the output is filled, center the image, and crop overflow. Mixed scale,
orientation, aspect ratio, and resolution therefore do not distort the image
or force all outputs to share one rendered buffer size. Output geometry is a
rendering concern only and does not participate in time or solar selection.

The desktop process does not add the greeter's authentication-region dimming
layer. Wallpaper artwork is unobstructed unless an independent desktop shell or
the active Genkan locker places content above it. When `genkan lock` acquires
the compositor lock, the desktop wallpaper process remains an ordinary client
behind the compositor-owned lock surfaces and cannot affect lock visibility or
input isolation.

== Process and deployment integration

The wallpaper command is started inside the user session through compositor
autostart or an equivalent user-session service. Genkan will not modify a
validated desktop entry to wrap the selected session in a shell, start the
wallpaper from the pre-authentication greeter, or make desktop startup depend on
wallpaper readiness.

The NixOS module exposes Genkan-level wallpaper and solar choices. When solar is
enabled, the module enables GeoClue and installs the exact application
authorization needed by Genkan. Raw `services.geoclue2` settings remain host
configuration owned and are neither mirrored nor passed through Genkan's option
surface. Hosts with an existing GeoClue policy can still use normal Nix module
merging to refine that service independently.

The module must not globally replace a desktop environment's wallpaper manager
without an explicit Genkan wallpaper enablement. It documents the initially
supported layer-shell compositors and any compositor-specific requirement to
disable or avoid a competing wallpaper process.

Packaged dynamic HEIC assets follow RFD 2's immutable asset model: provenance,
rights, byte size, cryptographic hash, media structure, schedule metadata, and
delivery URL are recorded in the wallpaper manifest; Nix fetches them as
fixed-output sources; and the running wallpaper process never downloads media.
An administrative or user-owned local file remains supported without becoming
a URI or content-download mechanism.

== Failure and security boundaries

Wallpaper operation is decorative. Failure to connect to GeoClue, decode a
frame, allocate a buffer, configure an output, or update at a schedule boundary
must not terminate a login or lock screen, release a session lock, affect PAM,
or prevent greetd from starting a selected session.

The desktop command may terminate when its compositor lacks the required
wallpaper protocol or the Wayland connection is permanently lost. A per-output
surface or allocation failure removes or freezes only the affected presentation
where practical. Decode failure retains the last displayed valid frame; failure
before one is available uses the primary image or generated background in login
and lock consumers. Diagnostics are bounded, single-line, and exclude
user-controlled metadata contents.

HEIF parsing occurs in a worker isolated from interaction and Wayland dispatch.
Frame and notification queues are bounded. Decoder retries and GeoClue retries
use bounded delays and cannot create a busy loop. Wallpaper metadata never
becomes a command, path, desktop identifier, D-Bus destination, log format, or
shell input.

== Verification

The implementation must provide deterministic evidence for:

* parsing valid `h24`, `solar`, and `apr` metadata and preserving top-level
  image ordering independently of HEIF item identifiers;
* rejecting malformed Base64, XML, property lists, image indices, dimensions,
  numeric values, and excessive resource declarations without panic or
  unbounded allocation;
* correct local-time selection before, at, and after each boundary, across
  midnight, daylight-saving changes, time-zone changes, suspend, and clock
  jumps;
* reduced-motion switching and normal bounded crossfades without blank,
  stretched, stale, or partially allocated frames;
* solar selection from a deterministic injected location and date, including
  GeoClue timeout, denial, coarse accuracy, polar conditions, and fallback;
* proof that ordinary `h24` operation makes no GeoClue request and that solar
  enablement requests only city-level accuracy;
* layer-shell output addition, removal, resize, transform, mixed scale, and
  compositor rejection with no input surface or exclusive area;
* aspect-preserving cover rendering on laptop, 1080p, 4K, ultrawide, portrait,
  and mixed-output layouts;
* stable memory while changing repeatedly between high-resolution HEIC items;
* coexistence with the session locker, including complete wallpaper occlusion
  while locked and restoration after explicit authenticated unlock; and
* package construction and headless compositor smoke checks on x86_64-linux and
  aarch64-linux.

Schedule and solar tests use injected clocks and locations. Graphics tests use
a small committed or reproducibly generated HEIC fixture with visibly distinct
frames and known metadata, so CI never waits for real time or contacts a live
location provider. Representative desktop transitions and multi-output states
are captured and visually inspected in addition to protocol and pixel checks.

== Deferred work

The first implementation does not include GNOME Shell, KDE Plasma, or
X11-specific wallpaper adapters; automatic desktop light/dark preference
discovery; direct HDR output; HEIC authoring; remote wallpaper downloads;
per-output source selection; parallax; weather-dependent schedules; or exact
reproduction of undocumented macOS solar interpolation. Each requires a
separate compatibility, security, and resource decision after the common HEIC
engine and layer-shell desktop path are verified.
