= RFD 1 Tahoe-inspired greeter interaction and visual design

== Goal

Give Genkan a coherent login-window flow in which a person can recognize the
selected account or choose another before responding to authentication prompts.
The interface follows the macOS Tahoe 26 login window and lock screen as
closely as Linux licensing allows, while preserving the security, protocol,
session, and power boundaries of a Linux greetd frontend.

== Context and reference

The current interface places the clock, identity, authentication prompt,
session selector, status, and power controls in one large translucent panel.
That treatment obscures the account-selection step and makes the password form
look like a conventional application form rather than a system login window.

Tahoe's login window is the reference. After a restart it uses the same
layout as the lock screen: an undimmed full-screen wallpaper, a short date
above a large glass clock near the top center, a small avatar, name, and
password pill near the bottom center, and status items at the upper right.
Apple also supports both a list of users and name/password fields depending on
administrator policy. Genkan follows Tahoe's layout, proportions, typography,
and behavior, measured from real captures and recorded in
link:../../docs/design-system/README.md[the design system]. It does not copy
Apple artwork, fonts, symbols, hover-revealed controls, or branding.

The reference material for this direction is:

* https://support.apple.com/guide/mac-help/welcome/26/mac[macOS Tahoe User Guide]
* https://support.apple.com/guide/deployment/login-window-payload-settings-dep2a822b29/web[Apple Platform Deployment: Login Window settings]
* https://developer.apple.com/design/human-interface-guidelines/materials[Apple Human Interface Guidelines: Materials]
* https://support.apple.com/guide/mac-help/turn-accessibility-options-login-window-mchlaa57f797/26/mac/26[Accessibility options in the login window]

== Decision

Genkan uses two explicit presentation states without requiring an unnecessary
selection step at every login. It initially selects the most recently logged-in
eligible account and shows its authentication state, like the Tahoe Login
Window. A visible Change User action enters account selection whenever another
eligible account exists; account discovery never depends on hover. Selecting a
tile establishes a greetd authentication attempt for that username and returns
to the selected-account state with whatever prompt greetd/PAM supplies.

The layout has no enclosing panel. The date and time sit near the top center.
The selected account and current prompt, or a row of accounts, sit small and
low at the bottom center. Session choice and power actions are menus in a
status area at the upper right, beside the keyboard layout and network status.
Authentication status stays adjacent to the prompt it describes. Exact values
are owned by link:../0005/README.adoc[RFD 5] and the design system.

The initial implementation continues to discover identities through
AccountsService. Selection precedence is an administrative `--username`
override, then the eligible account with the unique greatest positive
AccountsService `LoginTime`, then a sole eligible account. If login recency is
unavailable, zero, or tied for multiple accounts, Genkan opens account selection
instead of guessing. Genkan does not persist a second last-user record, infer or
synthesize an identity, or accept an arbitrary username when policy exposes
only a list of discovered accounts.

An administrative username override pins that identity and does not combine it
with AccountsService discovery or expose Change User. The remaining precedence
rules apply only when no override is configured.

`LoginTime` is ranking metadata, not an eligibility requirement. Failure to
read it does not discard an otherwise eligible account; that account simply has
unknown recency. Genkan never updates AccountsService login history itself.

Change User immediately invalidates the active attempt, clears the response,
and visually enters account selection. Genkan concurrently enters a
noninteractive cancellation state and sends `CancelSession`; account tiles may
render immediately but cannot start another attempt until cancellation
succeeds. Normally this is imperceptible. If cancellation is slow, the selector
shows bounded progress without moving the layout. If it fails, Genkan preserves
the selector, reports a recoverable error, and offers retry; it must not call
`CreateSession` for any account until cancellation succeeds. Late responses
from the invalidated attempt cannot change presentation state.

== Interaction states

=== Account selection

The account-selection state presents one avatar and name per eligible account
in a centered row near the bottom of the screen. Eligible retains the
existing AccountsService policy: a listed cached user with a valid username that
is neither locked nor a system account. Failure to load one object does not hide
other valid accounts; when none remain, the first discovery error is reported,
or the empty eligible-set error is reported when discovery itself succeeded.

Accounts use bounded display names and generated initials; the
credential-handling process does not decode user-controlled avatar files. The
username is shown as secondary text whenever display names would otherwise be
ambiguous, preventing duplicate or truncated names and
identical initials from becoming ambiguous. The pinned iced backend does not
expose semantic accessible names; publishing a combined display-name and
username label remains a framework-bound follow-up rather than a parallel tree
that could diverge from widget state. The upstream availability criteria are
recorded in link:ACCESSIBILITY.adoc[accessibility verification]. Keyboard focus,
pointer activation, and touch activation have equivalent results.

The row wraps and scrolls for large account sets. Scrolling keeps the clock
and status regions stable and preserves a visible focused account.

=== Authentication

The initially selected or newly chosen identity remains visually prominent
while account tiles give way to the current greetd prompt. The response field
and submit action form one compact control. The prompt label, field, error, and
progress message remain close enough to read as one unit. Change User is visible
whenever another eligible account exists and switching is valid.

dimensions, iconography, colors, or widget styling.

== Authentication behavior

The password state is only an example. Genkan renders every greetd prompt in
sequence, including visible and secret responses, and does not assume one
password exchange. Informational and error messages remain bounded and are
presented without collecting a response when the protocol does not request one.
Only greetd validates credentials and starts the selected session; Genkan never
validates, persists, or logs PAM responses.

Protocol acknowledgement for informational and error messages remains
automatic so Genkan does not add a non-protocol Continue step. The latest such
message remains visible alongside the following prompt until a later message,
successful authentication, account change, retry, or terminal failure
supersedes it. Consecutive messages therefore remain protocol-correct without
flashing important instructions too briefly to read.

Input is accepted only while the active attempt is waiting for a response.
Account and session changes are disabled during protocol transitions where
changing them would race authentication or session startup. Failed
authentication returns to a recoverable state without restarting the greeter.

== Output placement

Cage keeps one window covering the full desktop, so Genkan decides where its own
interface appears. The greeter presents authentication on exactly one output,
called the authentication output, and leaves the remaining outputs on
unobstructed wallpaper without account tiles, prompts, notices, or utility
controls.

Selection is deterministic and shared with the session locker. An explicitly
requested connector wins when it is present; otherwise Genkan prefers the first
connector name other than `eDP-1` in lexicographic order, falls back to `eDP-1`
when no other named output exists, and accepts an unnamed output only as a last
resort. `--authentication-output DP-2` is an administrative override like
`--username`: a requested connector that is absent does not fail startup and
falls back through the same rules.

Placement is re-evaluated when outputs are connected, removed, rearranged, or
rescaled while the greeter runs. Losing the authentication output moves the
interface to the fallback output without restarting authentication or changing
the active attempt, and the layout preserves focus, caret position, and input
visibility across output removal and resize. The session locker reuses the same
policy; link:../0003/README.adoc[RFD 3] records the lock-side behavior.

== Notice placement and recovery

Messages belong to the operation that produced them rather than one global
authentication status slot.

[cols="1,2,2",options="header"]
|===
|Source |Placement |Recovery

|Account discovery or cancellation
|Within the account-selection region
|Retry discovery or cancellation without starting another attempt

|No valid Wayland session
|In the session menu and under the password pill
|Rediscover validated entries before authentication retry

|PAM prompt, information, or authentication failure
|Within the compact authentication unit
|Respond, retry, or use Change User when allowed

|greetd transport or session-start failure
|Within the authentication unit as a system login failure
|Cancel any surviving attempt, then retry without restarting Genkan

|logind power progress or failure
|Within the power alert, or under the password pill after it closes
|Dismiss or retry without replacing authentication status or input

|Preview explanation
|A persistent non-error preview indicator outside protocol notices
|No recovery action
|===

== Visual and material rules

The background fills the display and is not dimmed. It may be generated
artwork or a packaged wallpaper with explicit provenance and redistribution
rights; Genkan does not ship Apple imagery. Text over the wallpaper stays
readable through soft shadows and blurred glass behind small controls.

Translucent or glass-like material belongs to small functional controls and
focused surfaces: the password pill, menus, alerts, and status items. It must
not become a large decorative content panel behind the entire login flow.
Legibility and visible focus take precedence over transparency.

The layout should preserve hierarchy across common laptop and external-display
sizes instead of reproducing one screenshot's pixel coordinates. Long localized
prompts, bounded account labels, and status messages must wrap without pushing
the active input off screen.

== Session, accessibility, and power controls

The selected Wayland session remains visible but secondary. It can change only
while the authentication state permits it, and the selected validated desktop
entry remains the sole source of the command passed to greetd.

All interactive controls require visible keyboard focus and predictable tab
order. Account selection, prompt response, submit, Change User, session choice,
and utility actions must not depend on color, pointer hover, or icon recognition
alone. Accessibility and keyboard controls should appear only when implemented;
the interface does not show inert placeholders.

Initial focus is the selected account's response field when a prompt is ready,
the selected or first tile in account selection, and the safe Cancel action in a
power confirmation. Tab and Shift-Tab follow visual reading order. Enter or
Space activates focused tiles and buttons. Escape from account selection returns
to the prior selected account only when its attempt remains valid; after Change
User invalidates an attempt, Escape does not resurrect it. A modal traps focus,
visibly presents its action and consequence, and restores focus to its opener
when dismissed. Semantic modal and status announcements remain a follow-up for
an iced backend that meets the semantic-tree, Linux screen-reader adapter, and
selective-announcement criteria in
link:ACCESSIBILITY.adoc[accessibility verification].

Normal text targets at least 4.5:1 contrast and large text, focus indicators,
and meaningful control boundaries target at least 3:1 against adjacent colors.
Renderer-aware tests exercise 125 generated background combinations, control
states, and bright overlay underlays in both iced blend spaces. This is the
numeric acceptance boundary for the generated background; it does not claim an
exhaustive proof over every continuously antialiased edge.

Sleep, restart, and shutdown remain explicit, labelled actions in the power
menu. Restart and shutdown ask for confirmation in an alert; sleep acts
immediately, as on macOS, because it cannot lose work. Preview mode continues to simulate them. Production actions
remain logind requests and may expose a host kernel, firmware, or display-driver
problem; the UI must report a failed request but cannot claim to make suspend or
resume hardware-safe.

== Safe preview fixtures

Development preview is a deterministic presentation harness, not a partial live
greeter. It provides local fixtures for zero, one, many, duplicate-name, and
large account sets; visible and secret prompts; consecutive informational
messages; authentication, discovery, session, and power failures; cancellation
progress; and power confirmation. Fixture selection must not depend on the
development machine's accounts or services.

Preview never connects to AccountsService, opens `GREETD_SOCK`, sends a greetd
exchange or restart, or calls logind power methods. It records simulated actions
for assertions, clears simulated credential responses, and keeps all power
actions non-destructive. Negative side-effect tests protect these invariants.

== Boundaries and non-goals

This RFD defines a boot greeter, not a desktop lock screen, fast-user-switching
service, or session locker. It does not copy Apple assets, fonts, or symbols,
hide required controls behind hover, introduce arbitrary shell commands, or
move authentication ownership out of greetd/PAM.

It also does not choose final wallpaper artwork or require account photographs.
Those assets require a separate provenance and packaging review. Exact values,
animation timing, and icon design live in the design system and RFD 5.

== Alternatives considered

=== Keep the single application-style panel

This minimizes code movement but keeps account selection visually subordinate,
groups unrelated system controls together, and conflicts with the chosen
login-window hierarchy.

=== Reproduce Tahoe behavior exactly

Originally rejected, and adopted in part by the 2026-11 amendment. Genkan now
follows Tahoe's layout, proportions, typography, and visible behavior. It still
does not copy controls revealed by hover, behavior greetd does not provide, or
Apple's artwork, fonts, and symbols.

=== Show username and password fields for every installation

This avoids account tiles but bypasses AccountsService as the normal identity
source and weakens the clear identity-before-authentication flow requested for
Genkan.
Administrative username overrides remain available without becoming the normal
interactive path.
