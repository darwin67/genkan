= RFD 5 Shared design system for login and lock presentation

== Goal

Give Genkan one named, enforced vocabulary for spacing, typography, color,
material, shape, and control geometry, and one set of reusable presentation
components built from it. The login greeter and the session lock must draw
from the same vocabulary so that they look like one product, and a contributor
adding a control should choose from existing tokens and components rather than
inventing new values.

This RFD changes how presentation is specified and constructed. It does not
change authentication, session, power, or lock lifecycle behavior.

Implementation progress is tracked in
link:IMPLEMENTATION.adoc[the implementation checklist].

[[context]]
== Context

link:../0001/README.adoc[RFD 1] established the greeter's interaction
hierarchy and its visual and material rules: restrained translucent material on
small controls, one shared radius, border, and focus language, and minimum
contrast targets. It deliberately left "exact spacing, animation timing, and
icon design" as implementation details. RFD 3 then added a session lock with
its own presentation, and RFD 2 and RFD 4 added photographic and dynamic
wallpapers behind both.

The shared radius, outline, focus ring, and a set of material colors did land
in `src/theme.rs`. Everything else is chosen at each call site. At the time of
writing, `src/app/view.rs` alone uses:

[cols="2,1,3",options="header"]
|===
|Property |Distinct values |Values

|Text size |9 |13, 14, 15, 16, 18, 22, 24, 28, 80
|Padding |10 |`[7,12]`, `[8,14]`, `[9,14]`, `[9,15]`, `[10,18]`, `[12,18]`, `[24,16]`, `[28,30]`, `[42,24]`, 30
|Spacing |10 |0, 2, 6, 7, 8, 10, 12, 14, 22, 28
|===

`src/theme.rs` contains 26 raw RGB(A) literals with no role names beyond the
function that uses them. The lock overlay in `src/locker/mod.rs` is drawn by a
separate CPU text and shape renderer with its own geometry constants and ten
further font sizes (14, 15, 16, 17, 20, 22, 27, 34, plus minimum sizes 7 and
8), none of which are derived from the login values.

The observable consequences in the current reference and preview captures are:

* Buttons with the same role have different padding and text size: Retry,
  Change User, power actions, discovery retries, and the session selector each
  define their own.
* The session menu uses an unrelated saturated blue for hover and selection
  instead of a material or accent role, and its geometry is fixed in pixels
  independently of the controls around it.
* Login and lock present the same authentication field differently: login
  shows a label above the field and a drawn submit arrow, while lock shows the
  prompt as a placeholder and a `↵` glyph. Each has its own `initials()`
  function.
* There is no text-overflow policy. Each call site independently picks
  word-or-glyph wrapping, a fixed height, or both, so long names grow tiles
  without bound in one place and are clipped mid-glyph in another. The lock
  renderer already fits single lines; login does not reuse that behavior.
* Dialog, menu, and badge opacity were chosen by eye, so a power confirmation
  dialog is translucent enough for the avatar beneath it to show through.
* Status and error text has no shared component, so its alignment depends on
  the parent column; a power error is right-aligned in the centered compact
  layout.
* The session-lock compositor dims the entire composed frame, including the
  authentication overlay, so lock text renders at 80% white. There is no rule
  that a scrim applies to the background layer only.

Several other defects found in the same audit are behavioral rather than
presentational: the login forces the compact layout whenever a prompt is
active, any non-ASCII display name forces the compact layout, and a failed
authentication requires an extra Retry activation before the user can respond
again. A design system does not fix those, and this RFD does not claim to. They
were fixed separately in pull request 58; the screen-region rules below keep
them fixed.

== Decision

Genkan adopts a three-layer design system whose values come from
link:../../docs/design-system/README.md[`docs/design-system`]:

. *Tokens*: a renderer-independent module of named constants for colors,
  type styles, spacing, radii, and sizes. Tokens are plain Rust data with no
  iced dependency, so the iced greeter and the lock's CPU renderer consume the
  same values.
. *Components*: iced builders for every recurring piece of the login and lock
  screens, each taking a semantic variant rather than raw sizes or colors.
. *Screen regions*: a fixed set of named regions anchored to the screen edges,
  so a control's position is a property of the screen template rather than of
  the current authentication phase.

The visual direction is the macOS Tahoe login window and lock screen, as
amended in link:../0001/README.adoc[RFD 1]. After a restart, Tahoe's login
window uses the same layout as its lock screen, so login and lock share one
composition and differ only in what lock omits.

The lock renderer does not adopt iced widgets (see
<<alternatives-considered>>). It adopts the token layer and a small set of
shared, renderer-independent helpers so its geometry, type, color, and text
policy are derived from the same source.

Literal sizes and colors outside the design module become a verification
failure, so drift is caught in review rather than in screenshots.

== Tokens

`docs/design-system/tokens.json` is the reference for every value. It was
measured from photos and a video of a real Tahoe login window and lock screen
on a display scaled to 3008×1692, so values are logical points, accurate to
about ten percent. `src/design/tokens.rs` mirrors it as Rust constants, and a
unit test parses the JSON and fails when the two disagree.

Token names describe roles, not values. The families are:

[cols="1,3",options="header"]
|===
|Family |Contents

|Color |Text roles (`text-primary`, `text-date`, `text-secondary`, `text-placeholder`, `text-menu-heading`), the glass clock, the password pill's glass and border, the avatar gradient and ring, status-bar highlight, menu and alert materials, `accent`, `pill-secondary`, `focus-ring`, and `scrim-modal`
|Type |Inter styles for the clock, date, initials, account name, pill, status bar, menus, PAM messages, and alerts, each with size, line height, and weight
|Spacing |Status-bar insets and gap, identity gap and bottom inset, clock top inset, account gap, menu and alert padding
|Radius |Status-bar item, menu item, pill, menu, alert button, alert, and round
|Size |Pill, submit circle, status-bar item, menu item, alert button, avatar, account width, menu, alert, and message width
|===

Rule: the wallpaper is never dimmed. Legibility comes from soft text shadows
and blurred glass behind small controls. Only an alert darkens what is behind
it, with `scrim-modal`. The session-lock crate's wallpaper dimming therefore
becomes a caller-supplied factor, set to none by default.

Rule: blurred glass samples the wallpaper. Genkan owns the wallpaper pixels on
both screens, so the pill, menus, and alerts blur a copy of the frame behind
them instead of relying on compositor support.

== Components

Components live in `src/design/components/` and are the only place that
applies tokens to iced widgets. Each has guidelines and a preview in
`docs/design-system/components/`.

[cols="1,3",options="header"]
|===
|Component |Contract

|`StatusBar` |The top-right row: session item and power item (login only), keyboard layout, and network status. An item whose menu is open is highlighted.
|`Clock` |Short date above the large glass time, from one formatting source shared by login and lock.
|`Avatar` |Initials over the avatar gradient with a ring; the focus ring when focused in an account row. Initials come from one shared, renderer-independent function.
|`PasswordField` |The grey glass pill that collects every PAM response. Placeholder when empty, dots for secret input, text for visible input, an outlined submit circle once there is input, a Caps Lock glyph while Caps Lock is on, and a horizontal shake that clears it on rejection.
|`StatusMessage` |PAM text centered on the line under the pill, or above it for a prompt. Absent unless PAM sends text.
|`AccountRow` |Avatars with names in a centered row for choosing an account; names truncate with an ellipsis.
|`Menu` |The session and power dropdowns from status-bar items, with a heading, a highlighted item, and a check mark on the selected item.
|`Alert` |The Restart and Shut Down confirmation over `scrim-modal`, with Cancel focused initially.
|===

Overflow is decided by the component, not the caller. Names and identifiers
truncate on one line; PAM text wraps up to `message-width` and a bounded number
of lines. The shared single-line fitting helper is renderer-independent: it
takes a width-measuring function, as the lock's `fit_single_line_by` already
does, so iced and the lock renderer share its truncation logic.

== Screen regions

Every output that shows authentication uses the same regions, anchored to its
edges in logical points:

* `status`: `bar-inset-top` from the top and `bar-inset-right` from the right;
* `clock`: centered, `clock-top` from the top;
* `identity`: centered, with the pill `identity-bottom` above the bottom edge.

Rule: the region a control occupies never depends on the authentication phase.
The phase changes what the identity region shows (one account, an account row,
a prompt, a message), not where the status bar, clock, or identity sit.

Rule: layout is chosen from available size and measured content, never from the
character set of the content.

Outputs too short for the clock and identity regions without overlap scale the
clock down; everything else keeps its point size, as macOS does. Outputs that
do not show authentication show the wallpaper only.

== Lock renderer adoption

`src/locker/mod.rs` keeps its CPU renderer. That renderer keeps response text
out of the glyph pipeline and draws only masked characters, and this RFD
preserves that boundary. It changes as follows:

* Font sizes, colors, pill geometry, avatar size, and spacing are read from
  tokens and scaled by the renderer's render scale.
* `initials()` and single-line fitting come from the shared helpers.
* The overlay draws the status bar (without session and power items), the
  clock, and the identity region exactly as login does.
* The wallpaper is no longer dimmed.

Rendering the lock overlay at the output's logical size instead of the current
fixed canvas, and fractional-scale support, are tracked with
link:../0006/README.adoc[RFD 6].

== Typeface

Login (iced) and lock (cosmic-text) currently each resolve the generic
sans-serif family through the packaged fontconfig, which contains DejaVu. They
match only by coincidence. The design system names one typeface token that both
renderers load explicitly.

That typeface is Inter. It is the closest freely licensed match for the
system font of the macOS login and lock screens Genkan follows, which cannot be
shipped on Linux. Inter is released under the SIL Open Font License, so Genkan
bundles a pinned copy in the package, records its version, license, and hash
alongside the wallpaper provenance, and loads it by file in both renderers
instead of resolving a family name through fontconfig. A rounded face for the
clock, closer to the macOS lock-screen clock, is a separate open question.

== Verification

* The existing WCAG contrast tests in `src/theme.rs` move to the design module
  and are written against color roles. Text over the undimmed wallpaper is
  checked with its text shadow against samples of the packaged posters, not
  only the generated background.
* A unit test fails when `src/design/tokens.rs` and
  `docs/design-system/tokens.json` disagree.
* A repository check, run by `make verify`, rejects numeric literals in iced
  text-size, padding, spacing, and color constructors outside `src/design/`,
  and raw color or font-size literals in the lock overlay renderer outside
  token lookups. Tests and preview fixtures are exempt.
* Reference images and preview-evidence captures are regenerated deliberately
  for each visual change and compared against the design-system screens.
* Component tests cover each overflow policy with the existing long-name,
  duplicate-name, and long-prompt preview fixtures.

== Boundaries and non-goals

* No user-configurable themes, light appearance, or runtime theme files.
* No change to greetd, PAM, session validation, power, or lock lifecycle
  behavior. Moving the session and power controls into status-bar menus changes
  where they appear, not what they do.
* No semantic accessibility tree. That remains deferred under RFD 1's
  accessibility criteria.
* No Apple assets: no SF Pro, SF Symbols, Apple wallpapers, icons, or logo.
* Account photos are out of scope here; the avatar shows initials until a
  separate change adds sandboxed photo decoding.

[[alternatives-considered]]
== Alternatives considered

=== Tidy constants in `theme.rs` without a component layer

This is the cheapest change and would remove most duplicate values. Without
components and a literal check, call sites would continue to choose padding,
overflow, and alignment, and drift would return.

=== Adopt an external iced design system

Libraries such as libcosmic provide complete component sets, but they bring
their own visual language, pin iced forks, and add a large dependency to a
credential-handling process. Genkan needs a small, auditable set of controls.

=== Render the lock overlay with iced

This would let login and lock share components directly. It conflicts with the
lock renderer's constraints: it draws into compositor-owned session-lock
buffers, keeps response text out of the text pipeline, and must fail closed
independently of a GPU renderer. Sharing tokens and renderer-independent
helpers achieves visual parity without moving that boundary.

=== Generate Rust from `tokens.json`

A build step could generate `tokens.rs` from the JSON reference. A hand-written
mirror plus an equality test keeps the build simple, keeps every value visible
in review, and still catches drift.

== Open questions

* Does iced 0.14 provide ellipsis truncation natively, or does the shared
  fitting helper measure and truncate?
* How strong should the background blur be to match Tahoe's glass, and is it
  cheap enough on the software renderer?
* Does the shake animation need a reduced-motion alternative beyond clearing
  the pill?
