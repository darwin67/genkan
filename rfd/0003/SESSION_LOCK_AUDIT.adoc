= RFD 3 session-lock runtime audit

== Decision

Genkan does not use `iced_exwlshell` or `exwlshellev` as its lock security
boundary. The 0.20.0 release is useful as an implementation reference, but its
general-purpose event loop permits layer-shell and xdg-shell surfaces, exposes
an unrestricted unlock action, maps generic iced exit to
`unlock_and_destroy`, and calls `unlock_and_destroy` after a confirmed lock
receives `finished`. Those paths violate the lifecycle in this RFD.

The lock command instead delegates its security boundary to the small,
independently tested `genkan-session-lock` workspace crate in
`crates/session-lock`. The crate accepts presentation frames through a narrow
interface and has no dependency on iced, GStreamer, PAM, or greetd. It uses
Smithay Client Toolkit's protocol wrappers, which require an explicit
`SessionLock::unlock` call and otherwise destroy the protocol object without
requesting unlock. The upstream implementations consulted during development
are MIT licensed:

* https://github.com/waycrate/exwlshelleventloop/tree/efde776a41cb246cba48ff2165aa35efc14d3591[`iced_exwlshell` / `exwlshellev` 0.20.0]
* https://github.com/Smithay/client-toolkit/tree/v0.20.0[Smithay Client Toolkit 0.20.0]

No source was copied into this repository.

The production Nix package builds the default feature set. It never enables
`lock-test`; consequently the hidden deterministic authorization option is
absent from the production binary. Production authorization is received only
from the private `genkan-lock-auth` worker after PAM authenticates the real-UID
account.

== Runtime invariants

The runtime requires only `wl_compositor`, `wl_shm` with ARGB8888,
`wl_output`, and `ext_session_lock_manager_v1` for its security boundary.
Smithay Client Toolkit may also bind optional xdg-output metadata while
tracking outputs. Missing required globals, no outputs, unsafe surface
dimensions, rendering errors, and Wayland dispatch errors fail startup or
terminate the connection. There is no xdg-shell, fullscreen, or layer-shell
fallback.

One lock surface is created for every initial output and for each output added
later. Output removal drops only its corresponding local surface. Configure,
integer scale, and buffer transform changes redraw a correctly sized buffer.
Each output keeps at most two reusable buffers for its configured size, with a
256 MiB per-buffer and 512 MiB total client-mapping bound. Every retained
buffer owns an exact-capacity shared-memory pool, avoiding allocator growth
beyond that bound. A size change or output removal drops stale client mappings
immediately; Wayland keeps an already committed protocol buffer valid until
the compositor releases it. Post-dispatch maintenance resumes a coalesced
redraw after a current-size buffer release, so temporary double-buffer pressure
waits without allocating or failing. Animated content redraws are coalesced
behind compositor frame callbacks. Geometry changes commit after the current
event batch even when an older callback is outstanding, without requesting a
duplicate callback. Every committed buffer has alpha 255 and an explicit opaque
region. Wallpaper frames use precomputed
cover-cropping coordinates and the same darkening treatment as login; decoder
failure redraws the packaged poster or opaque generated fallback without
changing lock lifecycle state.

Only the protocol's `locked` event transitions the state to locked and writes
`READY` to `--ready-fd`. `finished` before confirmation is denial. `finished`
after confirmation, rendering failure, and compositor loss terminate the
runtime without calling `SessionLock::unlock`. The runtime has no generic iced
exit, close, or escape action.

The production unlock capability is reached only after the expected private
worker reports terminal PAM success, exits successfully, and still belongs to
the active attempt. The runtime then calls `unlock_and_destroy`, synchronizes
with the Wayland server, and exits. Testing can compile `lock-test` and request
the hidden one-shot authorization only after compositor confirmation.

Keyboard handling adds SCTK's `xkbcommon` feature and the exact `xkbcommon`
crate version recorded by `Cargo.lock`. PAM runs only in the separately
installed, unprivileged `genkan-lock-auth` worker. Its bounded versioned
socketpair protocol is implemented in `crates/lock-auth`. Protocol version 2
requires the compositor-gated `Begin` exchange; version 1 peers are rejected
before Wayland startup. Responses neither
implement revealing diagnostics nor cross a public socket.
The parent validates the worker's bounded `Ready` identity before requesting
the compositor lock, and sends `Begin` only after the compositor confirms that
lock. Worker processes are launched with `posix_spawn`, inherit only their
protocol descriptor, and verify the parent while installing a parent-death
signal. The parent owns each process through a pidfd and synchronously kills
and reaps it on cancellation, so a cancelled PAM transaction cannot outlive
its attempt or be confused with a reused process ID.

Every editable response has fixed 2048-byte capacity and is cleared in place
when edited, submitted, cancelled, or replaced. Both echo-off and echo-on PAM
responses remain masked in the rendered presentation; the worker bounds PAM
message and username scans before copying them.
The worker's local PAM trampoline clears every application-owned Rust response
and every C response allocated on an error path. After a successful callback,
Linux-PAM owns the response array and its disposal; the PAM ABI provides no
application callback for clearing that transferred storage after modules have
consumed it.
